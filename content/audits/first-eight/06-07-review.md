# Chapters 06–07 content review

Reviewed 19 September 2026. Scope: all six learning assets in `06-tcp-udp-ports` and `07-ethernet-switching`. No UI, application code, dependency, performance, or other-chapter changes were made.

## Result and teaching approach

Both lessons were substantially rewritten into a progression from the problem being solved, through mechanics and worked examples, to practical interpretation. Existing lesson H2 headings were retained for section-progress continuity. The language uses technical terminology with direct explanations, without invented personal experience, decorative analogies, or unsupported claims about what an examination will certainly contain.

The TCP lesson has about 2,050 prose words excluding tables, diagrams, code, facts and exam bullets. The switching lesson has about 2,160 by the same method. No ordinary prose paragraph exceeds 110 words. Both have facts, comparison tables, diagrams, annotated representative output, a misconception box, practical verification and a short exam-focus list. Chapter 07 retains nine H2 sections rather than merging an existing section identity solely to reach the authoring guide’s suggested maximum of eight.

Each chapter now has 16 questions, including two multi-select questions and seven exhibits; 20 flashcards; and two troubleshooting tickets. Chapter 06 retains ten command drills and Chapter 07 eleven. Each question has an explanation and a specific reason for every distractor. Single-answer positions are balanced: chapter 06 uses positions 0/1/2/3 in counts 4/3/3/4; chapter 07 uses 3/4/4/3. All scenarios supply their own relevant state instead of depending on unstated lab history.

## Corrected claims and primary evidence

The linked sources are also recorded in chapter frontmatter. These are original explanations and scenarios checked against protocol specifications and vendor documentation, not copied exam questions or purported examination dumps.

| Claim or correction | Evidence and how it was applied |
|---|---|
| TCP is a reliable, ordered byte stream; acknowledgments do not prove a business transaction succeeded | [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html), sections 2.2, 3.4–3.6 and 3.8. Worked examples distinguish byte delivery, cumulative acknowledgment, independent sequence spaces and application outcomes. |
| PSH and TCP segments do not delimit application messages | [RFC 1122](https://www.rfc-editor.org/rfc/rfc1122.html), section 4.2.2.2, and [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html). Removed the incorrect PSH “end of application message” claim and added a write-boundary question/card. |
| UDP header contents and absent UDP reliability must not be generalized to the application | [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html), [RFC 8085](https://www.rfc-editor.org/rfc/rfc8085.html), and [RFC 1350](https://www.rfc-editor.org/rfc/rfc1350.html). UDP carries length as well as ports/checksum; applications can add recovery. TFTP supplies the concrete example. |
| Flow control and congestion control solve different problems | [RFC 5681](https://www.rfc-editor.org/rfc/rfc5681.html) and [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html). Removed advanced throughput/cwnd/window-scale calculations and the categorical claim that routers have no part in congestion signaling. |
| Port categories are not universal operating-system ephemeral-port policies | [RFC 6335](https://www.rfc-editor.org/rfc/rfc6335.html) and the [IANA service/port registry](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml). Removed Windows/macOS/Linux/XP/Packet Tracer exact source-port assumptions. Retained the three registry ranges and common service assignments. |
| DNS TCP is not exclusive to zone transfers or universally required beyond 512 bytes | [RFC 7766](https://www.rfc-editor.org/rfc/rfc7766.html), sections 4–6. Lessons, questions, cards and commands consistently explain UDP/TCP queries and truncation retry without an obsolete fixed-size boundary. |
| FTP data behavior depends on mode; TFTP UDP 69 is the initial request destination | [RFC 959](https://www.rfc-editor.org/rfc/rfc959.html), data-connection discussion, and [RFC 1350](https://www.rfc-editor.org/rfc/rfc1350.html), initial connection protocol/TIDs. Removed any implication that every FTP transfer uses destination 20 or every TFTP packet targets 69. |
| Initial DHCP discovery is not a rule that all DHCP packets are broadcasts | [RFC 2131](https://www.rfc-editor.org/rfc/rfc2131.html), sections 3–4. Client/server UDP 68/67 are explicit, and subsequent behavior is deferred to the DHCP lesson. |
| Web transport has a modern UDP-based exception | [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html). HTTP/3 over QUIC is a concise exception, not a new advanced learning objective. |
| TCP resets, ping and port tests have different evidentiary limits | [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html), reset/opening rules; [Microsoft Test-NetConnection](https://learn.microsoft.com/en-us/powershell/module/nettcpip/test-netconnection). A reset establishes active rejection, not uniquely a stopped service; ping does not test transport/application acceptance. The lab can name a cause because it includes the deliberately changed server setting. |
| Router TCP state is local endpoint state, not all transit TCP traffic | [Cisco IOS XE TCP guide](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-addressing/b-ip-addressing/m_iap-tcp_for_xe.html). `show tcp brief` example and drill state this scope. [Microsoft netstat](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/netstat), [nslookup](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/nslookup), and [arp](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/arp) support Windows-specific alternatives. |
| Source learning and destination forwarding occur within a VLAN; clearing MAC and ARP tables are independent | [Cisco Catalyst 2960 MAC administration](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst2960/software/release/15-0_2_se/configuration/guide/scg2960/swadmin.html), [Cisco unicast flooding](https://www.cisco.com/c/en/us/support/docs/switches/catalyst-6000-series-switches/23563-143.html), and [RFC 826](https://www.rfc-editor.org/rfc/rfc826.html). Tables, labs, questions and tickets consistently separate source evidence, destination lookup and host next-hop resolution. |
| Dynamic aging/defaults/static commands need platform scope | [Cisco Catalyst 2960 MAC administration](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst2960/software/release/15-0_2_se/configuration/guide/scg2960/swadmin.html), Default MAC Address Table Configuration and command procedures. 300 seconds is expressly the reference IOS default; timer-range/capacity memorization and generic four-hour ARP claims were removed. |
| Flooding excludes ingress and ineligible ports; group traffic is not universally flooded | [Cisco unicast flooding](https://www.cisco.com/c/en/us/support/docs/switches/catalyst-6000-series-switches/23563-143.html), [Cisco 2960 IGMP snooping](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst2960/software/release/15-0_2_se/configuration/guide/scg2960/swigmp.html), and [IEEE group MAC guidance](https://standards.ieee.org/wp-content/uploads/import/documents/tutorials/macgrp.pdf). Port-state/VLAN exclusions are explicit in prose and exhibits; multicast snooping and reserved-group caveats replace blanket group flooding. |

## Lab and cross-asset consistency

Chapter 06 uses one 2960, PC-A `192.168.40.10/24`, and SRV1 `192.168.40.20/24`, with exact Fa0/1/Fa0/2 links, explicit access VLAN 1 configuration, DNS at `.20`, and no invented gateway for a same-subnet lab. HTTP and DNS are enabled separately. The TCP opening is distinguished from the UDP lookup; cached sessions/answers have a stated recovery method. Turning HTTP Off is the only fault and Step 7 explicitly restores it, retests both address/name access, and saves switch and topology state. The challenge supplies DNS observations and correct ACK arithmetic (`8001 + 1200 = 9201`; SYN ACK `8002`).

Chapter 07 begins with A/B/C on S1 Fa0/1/2/3 using `192.168.90.10/.20/.30` and `/24` masks. It separately controls ARP and MAC state for an unknown-unicast demonstration. It then moves B/C to S2 Fa0/2/3 and joins S1/S2 on Fa0/24 with explicit matching VLAN 1 access ports. Dynamic entries are expected on the uplink, not necessarily at the endpoint’s physical port. Timer/static changes are restored and saved before an intentionally wrong B static entry is introduced in Step 9. Step 10 removes that exact entry, verifies dynamic learning through Fa0/24, retests and saves. Every example MAC requiring substitution is identified; tickets using fixed MACs are self-contained scenarios.

The new tickets reinforce service-versus-reachability, incorrect DNS configuration, incorrect static forwarding, and harmless temporary unknown-unicast flooding. They do not teach unrelated advanced configuration under these chapter objectives. Explanations no longer equate many learned uplink hosts with an attack or one MAC move with a proven loop.
