# Command relevance review: chapters 00–15

Reviewed 27 September 2026 against the current lesson, guided lab and practice design of every chapter. The earlier command-trainer pass left all original items in place and expanded their explanations. This review changes the selection itself: a command appearing in a lesson is not automatically a command learners should memorize there.

The 138 original items now yield **96 exercises: 95 revised and retained, 43 retired, and one added**. The [item ledger](00-15.json) records a separate reason for each original identity and the new one. It also gives each chapter a practice purpose, demand level and review links. Retired practice remains in its named lesson, lab, other command owner or subnetting exercises; no lesson or lab was deleted or rewritten in this scope.

## What belongs in command practice

The [practice plan](../../PRACTICE-PLAN.md) distinguishes supplied setup from recall outcomes. The [opening practice design](../practice-design/README.md) and [09–23 practice report](../practice-09-23/README.md), including their author decisions, provide the intended progression. Each current command was compared with that chapter's lesson and lab, including its independent challenge, rather than accepted because a previous audit retained it.

- **00:** Six short tasks establish the complete mode/name/save/check workflow. All are core prerequisites, even without a separate literal exam bullet for hostname syntax.
- **01 and 02:** No command bank. Packet forwarding, table interpretation, topology and device roles are assessed through their labs and checkpoints. Supplied observation commands and interface descriptions are not promoted into premature memorization targets.
- **03:** Five inspection and recovery decisions. Commands that only inject the lab's forced-setting or shutdown faults are retired. The learner still observes those experiments in the lab.
- **04:** One address-and-mask construction task plus separate address/state, prefix, active-configuration and reachability checks. IPv4 removal remains optional. Repeated saving, administrative enablement and premature broad routing-table recall are removed.
- **05:** No command bank. Capacity, alignment and overlap remain substantial subnetting and lab work. Repeating the same interface command with three different masks does not create three useful syntax outcomes.
- **06:** No command bank. The required transport work is packet/socket interpretation. Optional Windows utilities and supplied DNS/ping setup are not transport-recall requirements.
- **07:** Four useful forwarding-table views answer different questions: complete state, one MAC, one local port and one VLAN. Static-MAC fault construction/removal, timer display and experimental clears remain supplied lab/reference material.
- **08:** Keeps the substantial local-access/SSH workflow because its parts make different decisions. Adds selection of the VTY context before authentication/transport tasks; removes another identical save task. The lower-privilege inspection task now uses the actual > prompt described in its scenario.
- **09:** Keeps VLAN creation, naming, access/voice policy and complementary verification. PoE work asks for evidence and restoration, rather than a separate recall task for disabling power to cause a fault.
- **10:** Retains replace/add/remove because the scope of each change matters. Retires the older optional encapsulation selector. Familiar VLAN and switchport queries return only with a new allowed-versus-active or configured-versus-operational decision.
- **11:** Keeps subinterfaces, tagged/native mapping, SVI creation, routing enablement, physical routed ports and the non-routing management gateway. Retires unqualified repeats of brief-address and trunk inspection; keeps checks specific to the newly taught interface roles.
- **12:** Begins with accessible neighbor evidence, then addresses configuration and direction policy. Drops the timer-display catalog. Transmit and receive remain separate because they change opposite discovery directions; brief and detailed views have stated, different information needs.
- **13:** Keeps active/passive choice, summary/member flags, partner identity, logical configuration context and routed-bundle role. Removing a member is bounded to a shut lab interface used in the documented correction. A fallback display and optional hash-inspection syntax are retired.
- **14:** Begins with operational state, then root placement and cost preference. Root macros, explicit priority and local cost make different decisions; another root-summary display and secondary sender-port tuning are removed. Tie-break reasoning remains in the lesson and questions.
- **15:** Tasks require the correct protection scope and trigger. Automatic errdisable-recovery policy stays optional reference rather than compulsory recall. Trunk PortFast remains an explicitly qualified extra exercise after the main set.

No bank is padded to a quota. The demand labels describe these command tasks, not the whole chapter: choosing or constructing one taught command is generally application, even when the task includes a symptom. Multi-observation diagnosis remains in the labs, questions and tickets.

## Exam relevance and primary sources

Cisco's [v1.1 objectives](https://learningcontent.cisco.com/documents/marketing/exam-topics/200-301-CCNA-v1.1.pdf) and [v2.0 objectives](https://learningcontent.cisco.com/documents/marketing/exam-topics/200-301_CCNA_v2.0_Exam_Topics_PDF.pdf) were opened during this review. Their verbs set the depth: conceptual prerequisites do not imply a CLI-recall requirement. The v1.1 discovery configuration scope and v2.0 documentation-validation scope are distinguished. Spanning-tree configuration is extra reinforcement under v1.1's interpretation objective and core under v2.0's configuration objective. PoE configuration likewise follows the selected track. Foundational dependencies such as IOS modes and the taught local SSH workflow remain part of the practical core.

Protocol/command checks used Cisco's [IOS CLI guide](https://www.cisco.com/c/en/us/td/docs/ios/fundamentals/configuration/guide/12_2sr/cf_12_2sr_book/cf_cli-basics.html), [EtherChannel configuration guide](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-17/configuration_guide/lyr2/b_1717_lyr2_9300_cg/configuring_etherchannels.html), and [optional STP features guide](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-12/configuration_guide/lyr2/b_1712_lyr2_9300_cg/configuring_optional_spanning_tree_features.html), alongside the platform-specific sources already attached to the chapters. The retained answers continue the documented lab command families rather than adding new advanced platform requirements.

## Verification and limits

- Reconciled all 138 original IDs plus the one new VTY-context ID against the actual final banks.
- All 96 retained/new exercises have a valid section link and compact hint/takeaway. Syntax annotations reconstruct the canonical answer exactly; no old note, purpose, before, verify or syntax-meaning fields remain.
- All 116 canonical/accepted command forms in this range pass the current command grader.
- Every learner review link resolves to an existing chapter. The VTY-context task precedes local login/transport tasks; discovery and STP begin with simpler observations.
- No Packet Tracer or physical-device execution occurred in this editorial pass. Source checks and app grading establish different things; neither validates an actual lab run or predicts an exam result.
